Session lifecycle facts worth knowing
  • Created on the first click, OnSession-Start fires, sticky to one app server, with session data also persisted so another server can pick it up on failover.
  • Soft timeout 30 min of inactivity — 15 min when PCI enforcement kicks in (payment added in checkout, or an agent on behalf). Clears privacy data and logs the customer out, but the id can reopen the session.
  • Hard timeout 6 hours — the session id becomes invalid regardless of activity.
  • session.privacy is cleared on logout; session.custom is not. Sensitive data goes in privacy, personalisation flags in custom.

The shared-session trap

dw.web.URLUtils.sessionRedirect(host, url) preserves the session across host aliases of the same site. You cannot share sessions or baskets across two B2C Commerce sites. It only works through the redirect link — if the shopper edits the URL or types it, a new session is created, and coming back through a redirect link discards the other basket.

Service framework configuration classic exam question

Three objects: service configuration (one per service), service profile (timeout, rate limit, circuit breaker — shareable), service credential (URL and auth — shareable). Registered in code through LocalServiceRegistry.createService with createRequest and parseResponse callbacks; types are FTP, HTTP and SOAP.

SettingGuidance
TimeoutAbove the third party's average response, but real-time calls stay under 5–10 s and as low as possible on the critical path to avoid thread exhaustion. Batch can afford 20–30 s.
Circuit breakerNeeds two numbers from the vendor: how many failures, in what interval. Without them you cannot configure it honestly — say so rather than guessing.
Rate limitStraight from the vendor's SLA, e.g. 50 calls/second becomes 50 calls per 1,000 ms.
Platform defaultsSOAP and HTTPClient default to 2 min storefront, 15 min job. A shorter script timeout wins.
SubtletyThe configured timeout is a connection and read timeout per hop, not a total. A 5 s timeout can still take ~12 s overall if the connect and each read individually stay under 5 s.

Worked example from the deck: OMS lookup, vendor average 500 ms, capacity 50 calls/s → timeout 500 ms, circuit breaker off (no data), rate limit 50 per 1,000 ms.

Job framework essentials

  • Prefer system job steps over custom code. Custom steps are task-oriented or chunk-oriented CommonJS modules described by a steptypes.json in the cartridge; pipeline steps are possible but discouraged.
  • Chunk step functions: read, process, write, total-count, before-step, before-chunk, after-chunk, after-step. Chunking gives progress granularity and bounded memory.
  • Exit status: return dw.system.Status; an unhandled exception is ERROR; returning nothing with no exception is OK.
  • Flows can be sequential, parallel or mixed. Steps have a scope — site or organization — and most import steps are organization-scoped.
  • Failure handling exists at step level (stop job, stop flow, continue), plus job-level email notification and hang detection.
  • Memory discipline: stream to file, read record by record, do not let memory grow with the result set, drop references so objects can be collected.
  • Transactions: commit in small units inside steps rather than wrapping the whole job — one optimistic-locking failure at the end of a million-record transaction loses everything.

Ordering rule of thumb: master catalog first, then non-dependent imports (storefront catalogs, price books) in parallel, then search index rebuild, then replication.

StateMeaningYour move
log_onlyNot enforced; Salesforce is gathering statisticsNothing yet

  • Softening from error to warn: Support only, on PRD/STG/DEV. You can export quota settings from any instance but import only into a sandbox — useful for matching dev to prod.
  • Read-only quotas have no warn threshold, e.g. object.ProductPO.readonly.
  • Set up email alerts on quota violations, and check the deprecation log on the same rhythm.

Caching and cache invalidation

  • Code replication and activation, and data replication, clear the page cache unless the job says otherwise. Cache clearing during a sale is how a good site becomes a slow site — allow 15 minutes for the web adapter cache to settle.
  • Geolocation data and coupons are the exceptions: replicating them does not clear the cache.
  • iscache of type daily expires every page of that type at the same coded time. Prefer relative expiry.
  • Need one product live now? Use page cache partitioning, not a full invalidation.
  • VaryBy makes customer groups and active promotions part of the cache key — the basis of the "dummy 0% promotion" personalisation trick.
  • URL diversity destroys hit rates: the web adapter keys on the URL including parameter order. Keep parameter order fixed; move per-shopper values behind a # fragment so the server never sees them.

Concurrency: optimistic locking

No locks are taken. Each object carries an Optimistic Concurrency Attribute; on commit the platform requires new OCA == old OCA + 1, otherwise the transaction rolls back with an optimistic locking exception.

  • Classic collision: storefront marks an order export-ready as the last step of order creation while an order-processing job starts modifying the same order.
  • Second collision: two editors saving the same content slot — the second save fails.
  • Avoidance: split large updates into many small transactions; keep storefront requests reading shared data and writing only shopper-owned data; use the locking framework for jobs that must be exclusive. Inventory is deliberately built to tolerate concurrent change.

Replication & environments

Data replication in one card

  • Staging is always the source. Targets are Production and Development. Nothing else replicates, and sandboxes are never in the flow.
  • Modes: transfer (copies into shadow tables and folders, production untouched) → publish (switches the pointers) → undo (switches back — one step only, the last one).
  • Under the hood the data sits in …$1 / …$2 tables with a view pointing at one of them; replication fills the other and flips the view. Table names surface in replication logs.
  • Two levels: global (org-wide configuration, object definitions) and site-level (catalogs, content, images). Granularity is fixed — a whole catalog, never a single product.
  • Not replicable: active data, batch processes, import feeds, custom error pages, customers and customer-group assignments, uploaded-but-not-imported files, gift certificates, inventory, job schedules and history, organization profile, payment information, order information, sitemaps, source code redemptions, users/roles/permissions.
Best practices that come up in interviews
  • Never during other jobs, never during the day, never during the POD maintenance window.
  • Separate transfer and publish for production so you can verify before going live; read logs on both source and target when it fails.
  • Rebuild search indexes and let them finish before replicating them; disable incremental and scheduled indexing on both sides — replication fails if an index is being modified.
  • Follow dependencies: source codes and coupons before or with campaigns, or you corrupt data. Object definitions may need a matching code replication.
  • Split the privilege: whoever defines a replication should not be the person who executes it.
  • Change metadata on Staging, then replicate object definitions outward. Do not edit cartridge paths or code directly on production.

Launch & operations

Launch checklist, condensed

  1. SRA with customer and SI; every launch blocker closed.
  2. Keys and certificates into the instance keystore for web services, SFTP and crypto — note the storefront TLS certificate is separate and goes to the eCDN keystore.
  3. eCDN and DNS: zone created, cloudflare-verify TXT record and CNAMEs in place, certificate uploaded (wildcard if you want dev and pre-prod aliases), enforce HTTPS, WAF reviewed.
  4. Error and maintenance pages uploaded through Business Manager as errorpages.zip — not part of the cartridge, shared across the realm, published by a job that runs every 2 hours, with aliases.json if one page serves several hostnames.
  5. Site preferences for Production and Development set on Staging using the Instance Type field so they travel with replication.
  6. Go-live case with Support to move the first site from Preview to Online (protected) — the deck says at least 7 days ahead, the notes 5 business days; Support does this only for the realm's first site and it cannot be reverted.
  7. Firewall: allow-list both your POD's outgoing IP and your DR POD's, or disaster recovery will fail on backend connections.
  8. Load testing happens before the first site goes Live, or the test orders land in GMV.

Security checklist

  • Validate twice. Client-side validation is UX; server-side validation is the control. Do not leak internal value lists into client checks, and do not treat a regex as a security boundary.
  • CSRF: dw.web.CSRFProtection, synchroniser token tied to the session, validated on protected requests. Force POST for sensitive submissions via middleware.
  • XSS: encode with <isprint> and its encoding attribute. Never eval() anything derived from input.
  • Subresource Integrity on third-party scripts — in SFRA, addJs and addCss take an integrity hash as a second argument.
  • Content Security Policy to allow-list script origins; eCDN WAF for layer-7 protection.
  • Secrets: never in version control. Encrypted service credentials are the exception, since the private key is POD-specific. Prefer Business Manager over cartridge storage for private keys.
  • Access: one OCAPI/API client id per consumer, least privilege, role-based permissions, no shared accounts, Account Manager with MFA for anything security-critical.
  • Logs: prove no PII or PCI reaches them; service comm logs are filtered through ServiceCallback methods.

The platform underneath

Platform topology: one realm on one POD

B2C Commerce is multi-tenant SaaS. You do not get servers, you get instances inside a realm, and the realm lives on a POD — a point of delivery in one region, with a designated disaster-recovery POD elsewhere. Everything you design sits inside these boundaries.

What the drawing tells you as an architect
  • The page cache is in front of your code. A cached page never reaches the application server, which is why cache hit rate is the single biggest performance lever and why anything that clears the cache is an operational event.
  • Threads are finite. A slow third-party call holds an application server thread. This is why service timeouts and the circuit breaker exist, and how a vendor's bad day becomes your outage.
  • The database is shared and governed by quotas. You cannot add indexes or tune queries; you work within the object model, and custom attribute joins bypass the ORM cache.
  • Region matters. The POD binds you to a region for latency, data residency and the outgoing IPs your client must allow-list — including the DR POD's.

Instances, code versions and the replication flow

Four instance types, and only one legal direction for data to travel. Getting this diagram wrong in an interview is fatal; getting it right explains half of the operational rules in the courseware.

Two consequences people miss: metadata changes belong on Staging and travel outward as object-definition replication, sometimes needing a matching code replication; and because the whole mechanism is a view switch between shadow tables, undo only reverses the most recent replication.

The caching stack, and what invalidates each layer

Performance work on this platform is almost entirely cache work. Five layers, each with a different owner and a different invalidation trigger.

The two design rules that follow: keep URLs canonical (fixed parameter order, per-shopper values behind a #) so layer 3 can do its job; and treat every replication as a cache event to be scheduled away from peak, using page cache partitioning or the newer granular replication events when you only need one product live.

Lesson 1 · Discovery & Design

1-1 · Requirement areas of a typical B2C site

Four functional zones, each with its own storage and interaction character:

  • Content (read-only): product, category and search pages; content assets or Page Designer; store locator if used.
  • My Account (read-write, personalised): profile, address book, payment instruments, order history through the OMS, loyalty integrations.
  • Checkout (read-write, personalised): basket, product line items, shipments, payment, order — often with live inventory checks and address verification.
  • Back office: backend integrations and customer service functionality. Capture these requirements separately.
Requirement questions the notes raise
  • Dynamic categorisation is not out of the box. Rule-based assignment usually ends up in middleware feeding Staging, and it costs the merchandiser manual control. The alternative is implicit search refinements rendering a category-like page, which may not scale across a large catalog even with caching.
  • Promotions cross-cut everything — home page, cart, checkout, grids, PDPs. Coupon error handling and messaging differ by promotion type and location, and retail-math rules must be documented for the OMS as well as the storefront.
  • Search needs explicit answers: how many search behaviours, paging rules, what happens with no results, too few results, too many, sorting and ranking rules, whether specific products get promoted.
  • Page Designer vs content assets: pages and components are stored as content assets but are not editable from the content asset list, and Page Designer content is not reachable through the OCAPI Shop and Data resources. Replication and indexing behave the same.
  • Checkout UX evidence: around 85% of checkouts on the platform are guest checkouts — do not force account creation, and put guest checkout first. Minimise live third-party calls once the shopper is in the funnel.
  • Login: the platform supports OAuth2 providers, so shoppers can sign in with an existing Google or similar account.
  • Payments: multiple payment instruments per basket are supported; asynchronous methods (PayPal-style redirects) mean the shopper leaves and returns before order creation.

1-1 · Storing data server side, in detail

Session

See the quick-glance card for the limits. Additional notes: the platform has no metadata for session custom attributes, so it can only evaluate a condition on one if the condition suits the actual runtime type. Unsupported values used to log a deprecation warning and behave undefined; from compatibility mode 19.10 they raise an exception.

Persistent business objects

Everything inheriting dw.object.ExtensibleObject can carry custom attributes through the metadata system — extend system objects to collect more data (an evening phone number on CustomerAddress, website data on Store, a monogram on a product). Objects holding sensitive data inherit dw.customer.EncryptedObject, whose subclasses cover payment instruments, customer profile and web service credentials.

Custom objects extend the model for genuinely new needs. The type is always organization-wide; instances can be site-specific or global. Canonical example: a NotifyMe object holding an email plus an out-of-stock product id, drained and purged by a daily job. Because of the quotas, custom objects suit temporary shopper-generated data or low-volume permanent data such as complex configuration — not unbounded growth.

Generic mapping
  1. Build a CSV of key→value pairs.
  2. Upload it (Administration > Site Development > Import & Export, or WebDAV, or HTTP client into IMPEX).
  3. Run a job with the ImportKeyValueMapping step, which converts it into an in-memory map and notifies every app server in the cluster. Modes: Replace, Delete, Merge.
  4. Read it with dw.util.MappingMgr.get(mapping, key).

Mappings must be imported on each instance separately and are global rather than site-specific.

File system and WebDAV
  • Every instance has both an embedded WebDAV server and a WebDAV client — but the client cannot talk to its own or any other instance's server.
  • Reachable locations: cartridges, log files, security log files, import/export. All force SSL; plain HTTP is refused.
  • In storefront context you cannot create a file (uploads are possible, subject to quotas); in job context there is no restriction beyond size. Look for Storefront Limit: 0 in the quota spec.
  • Static files (product images especially) live on the instance file system; XML feeds carry database objects only.
  • Import and export are chunked, so feed size is effectively unbounded — but uploads are capped, and the five-minute request timeout is why import/export must run as jobs. Jobs have no runtime limit. Zip large uploads; standard import files are gzip-compressed natively.
Custom cache

Defined by a JSON file referenced from the cartridge's package.json; accessed through dw.system.CacheMgr and dw.system.Cache. Entries are immutable copies, primitives and tree-like structures only. Three canonical use cases from the notes:

  1. Expensive derivation: a master product showing an "On Sale" banner if any variant is on promotion — iterating all variants per request is costly, and the answer cannot be persisted because promotion eligibility expires. Cache it for a few minutes.
  2. Third-party responses: in-store availability and prices held externally, cached briefly to cut live calls and page load time.
  3. Configuration as code: pull config from a JSON file in version control and hold it in cache for fast storefront access.

Keep caching enabled on production (Administration > Operations > Custom Caches) and read the cache statistics table, which reflects only the current active code version on the current app server.

1-1 · Storing data client side, in detail

None of this ships with SFRA; it is all additive. Cookies are sent on every request including static assets, so size directly costs performance — and consent law applies before you store or read anything. Web storage is plain text and 5 MB, so never credentials or payment data, and it blocks the main thread.

The modern pair is a service worker plus the Cache Storage API: the worker intercepts requests and decides whether to hit the network, and Cache Storage gives code-driven control instead of relying on HTTP headers. The community SFRA service-worker plugin uses this for add-to-homescreen, a staging cache-bypass button, full-page client-side caching aligned to server cache timing, partial caching for remote includes, and a custom offline page. Only non-personalised pages — delivery and returns, say — should be cached this way. IndexedDB is the asynchronous option when structured data or blobs are needed.

1-2 · Data model, mapping and migration

Mapping document per object: source of data (client database, OMS, B2C Commerce), each attribute, its data type, and any restriction imposed by the origin system. Decide deliberately whether to keep one mapping document or one per interface.

Modelling
  • Validity vs integrity: validity is correctness and reasonableness, integrity is completeness and wholeness. Business users and source-system SMEs own completeness; the implementation must protect correctness in transit.
  • Concrete example: an attribute arriving as the numbers 1 and 2 cannot simply be declared Boolean — either model it as it is, or map the two values explicitly.
  • Fix bad data in the source system, never in the consumer.
  • Transformation: best case, the source emits standard B2C Commerce XML. Otherwise transform file by file, streaming, with XMLStreamReader / XMLStreamWriter — noting the writer does not check well-formedness of its input. Most B2C schemas mark elements optional so you can send only what you need, and cross-element validation is minimal: category assignments referring to missing categories are ignored and logged.
Migration

At minimum a transform and load. Plan for: knowing the data (full audit of the source first), cleansing, testing throughout design and implementation, and a governance mechanism for tracking data quality — especially if migration will be repeated rather than one-off. Then segregate data that will actually be used from data merely being carried over: the classic call is a cut-off such as "customers with no order in two years do not migrate". Use deltas whenever you can.

1-2 · Custom attributes and query performance architect-level

Creating a custom attribute does not add a column to the object's table. Custom attributes, localisable system attributes and site-specific system attributes all land in a separate attribute-value table — PRODUCT_AV for products — keyed on a compound of object id, attribute name and locale or site.

The consequence: querying on any of those attributes forces a join between the main and AV tables, which bypasses the ORM cache. So for query performance, prefer non-localisable, non-site-specific system attributes. Custom objects are almost entirely custom attributes, which is why the best practice is to always retrieve a custom object by the value of its key attribute rather than querying other fields.

Volumes, complexity and the awkward questions
  • Key volumetrics map to object quotas; others only log. Quota overrides are possible but carry performance risk, and Performance Engineering monitors usage to allocate resources.
  • Combinations matter more than single metrics — product line items per basket times active promotions, for instance.

Gap analysis and risk

Gap analysis is current state → target state → steps, run as: describe the area, identify improvement areas, set targets, describe the improvement step, implement and review. Prioritise so business-critical gaps go first. For B2C specifically: which features are wanted, what the chosen reference app already does, and whether each gap is new code, new content or new configuration.

Risk work is identification then assessment, qualitative and quantitative. Two worked examples:

  • Data residency: launching in a country requiring customer data to stay on local soil where Salesforce has no data centre. Mitigation: keep only an identifier and email in the B2C profile, hold the rest in CRM, and persist locally only transiently.

2-1 · Version control and release management

  • Git is the platform's preferred VCS. Centralised systems lock files on a client-server model; distributed systems mirror the whole history per developer.
  • Divide and conquer: code and test data may not belong in the same repository as configuration and production data. Drivers are asset type, fine-grained permissions (merchants may have limited or no repo access), and differing responsibilities and release cycles.
  • Version as little as possible and as much as necessary — test scripts, test data, compiled distribution vs source, documentation.
  • Never version sensitive data. Encrypted service credentials are the exception, because they can only be decrypted in the client's realm with a POD-specific private key.
  • Git Flow (master + develop, plus feature, release and hotfix branches) suits scheduled releases and larger teams. GitHub Flow (one always-deployable main plus descriptive feature branches) suits smaller, faster teams. Forking and merge requests are legitimate too.
  • Semantic versioning — MAJOR for incompatible API change, MINOR for backwards-compatible functionality, PATCH for backwards-compatible fixes — is used across all SFRA repositories.
SFRA versions specifically

Format v<major>.<minor>.<patch>, e.g. v3.3.0, with a matching Git tag. Development happens on the integration branch and merges to master; every increment gets a tag, but only versions tested against the full plugin suite are labelled releases — the rest are pre-releases and may be unstable. Practical rule: check out tags labelled as releases, and check out the same tag across every SFRA repository, or you cannot know the pieces are compatible.

2-2 · Trust: security implementation

The full security detail is in the quick-glance security card; the notes add specifics worth keeping:

  • Layered validation: client-side validation gives legitimate users immediate feedback on typos; server-side validation stops the attacker posting directly to the endpoint. Both, always, and the server one is the control.
  • Two validation anti-patterns: putting so much logic client-side that you hand attackers the list of valid values, and relying on validation as the whole defence — regular expressions in particular are hard to verify exhaustively.
  • Script injection: the usual root cause is eval() on tainted input. The method is deprecated; avoid it.
  • CSRF: synchroniser token pattern, random per-session token, validated server-side, request rejected on mismatch — effective because the attacker cannot know the token.
  • Subresource Integrity exists because a compromised CDN can rewrite the files every site fetches from it. SRI pins the expected content.
  • CSP lets you declare which origins may serve executable script; a compliant browser then ignores everything else, including inline script and event-handler attributes.
  • eCDN WAF adds layer-7 protection — layer 7 being the application layer, where HTTP requests live.

2-2 · Performance, modularity and localisation

Three performance areas

Server side: ISML templates, scripting, local vs remote includes. Client side: JavaScript, CSS, vector graphics, custom fonts. Integration: asynchronous through jobs, synchronous on the storefront or server to server. Instructor prompts for best practices: avoid business logic in templates, get remote-include caching right (price and timestamp), consider a service worker for client assets.

Modularity

Decomposition into smaller programs with standard interfaces — in this platform, cartridges scoped to a function plus CommonJS modules. Example: tax calculation behind a module, so callers do not know whether the answer came from the platform or a third party.

  • Modules are .js (or legacy .ds) files in a cartridge's script folder, or in the peer modules folder for globally shared and third-party modules.
  • Prefer require() over importPackage() — e.g. require('dw/system/Transaction').
  • Scope your requires. A require is a real function call, not a compile-time import. Requires at the top of a controller execute on every request, loading modules that the current path may not need; if every module does this, everything loads every time. Move non-API requires into the function bodies that use them.
  • SFRA customisation without touching base: at least one custom cartridge per implementation (more if you plan several sites, so brand or locale specifics separate cleanly); override a template by putting a same-named file in a cartridge earlier on the path; extend models to add data, add models, or swap them for another framework; customise controllers and routes with append and prepend in preference to replace. Cartridge path resolves left to right.
Internationalisation and localisation

Everything from business objects to the storefront is localisable. Steps: identify what needs localising (content assets, products, product attributes, currency), decide the approach, identify the languages and how they relate, and configure locale settings at organisation and site level. Two template strategies — one template set with externalised strings in resource files (recommended), or a unique template set per locale. Locale fallback and context-specific customer groups round it out; hub sites can segment by brand, country or lifetime value.

2-5 · Load testing

Load tests prove the platform plus the application can carry expected traffic, and expose inefficient custom code, customisations and integrations. Salesforce recommends load testing every new storefront before launch, and partners with Xceptance — though customers may choose their own vendor. Targets are in the numbers card.

Success criteria, and why percentiles

Averages compare runs conveniently but blur outliers; percentiles let you set specific optimisation goals and judge outlier influence. A successful test has no timeout-related errors and no server errors (4xx/5xx), and no functional errors caused by load. Occasional isolated spikes are acceptable; spike clusters and anything beyond 30 seconds are not.

Plan and prerequisites

For scripting: main page development complete with only bug fixing allowed; functional tests passed; enough catalog and product data to exercise paging, infinite scroll and refinements; external systems available and configured; a predictable, stable test system; Business Manager access including page cache, jobs, service framework and log files.

For execution: the execution environment (production instance or loaner realm) available and configured; target numbers known; test data as close to go-live state as possible (customers need not be imported); jobs configured and active; external systems available as test, mock or production; external parties informed so they do not throttle or shut down suspecting a denial-of-service attack; and a ticket with Salesforce so the realm is sized and green-lit.

Lesson 3 · Integration & Customizations

3-1 · Integration approaches

The strategy matrix is in the quick-glance card. Additional substance from the notes:

  • Design third-party calls stateless. For tax, send the whole basket and get tax for every line item back. Iterating line item by line item means tracking state, handling partial failure, and risking the eight-HTTP-requests-per-page storefront quota.
  • Asynchronous best practice: implement the process with the job framework split into reusable steps, and do the actual communication — file upload and download, API and web service calls — through the service framework.
  • Loose coupling is defined against coupling as the degree of interdependence between modules. Loosely coupled components make few assumptions about each other, so they break less when the other changes. The practical payoff is fault tolerance: assume every integration can fail, decide how it recovers, and decide what the shopper sees — with a different answer depending on whether it is on the critical path.
  • Transfer server: usually customer-provided SFTP, configured with file retention, security and access restriction. It decouples the integration and lets other systems consume the same files. Consider PCI/PII in files and whether they need encryption at rest. WebDAV over HTTP and other proprietary services can also play this role.

3-4 · Pipelines and controllers: coexistence

Pipelines are XML workflows proprietary to the platform, visualised only in UX Studio. Controllers are CommonJS modules. Both produce the same URL shape — Home-Show is Pipeline-Subpipeline or Module-ExportedFunction interchangeably.

  • Both can live in one cartridge in their respective folders. Same name → the controller wins. The platform checks for a controller on the cartridge path before looking for a pipeline, and does not verify that the function or start node actually exists.
  • Best practice is not to mix them in a single cartridge: put controllers in a separate cartridge so you can build incrementally and fall back by removing the controller or the cartridge from the path.
  • Only call pipelines that are outside the current cartridge or needed to integrate a separate cartridge.
  • Remote includes behave identically either way.
Calling across the boundary

Controller → pipeline: works like a subroutine call and can take arguments — except with an interaction-continue node, where the template renders, control returns to the controller immediately, and the follow-up request for the continue branch goes straight to the pipeline processor, bypassing the controller.

Pipeline → controller: not possible with call or jump nodes. A script node must require the controller. And you should not call controller routes from a pipeline at all — only local functions that are not URLs, which ideally should not be in the controller in the first place but in a module under scripts. Routes carry middleware in SFRA (guards in SiteGenesis) that provide security checks; bypassing them bypasses the checks.

Transactions

Pipelines define transactions implicitly and explicitly through pipelet attributes and node transaction-control values (begin, commit, rollback, save point). Controllers use dw.system.Transaction — wrap() for implicit, begin() / commit() / rollback() for explicit.

  • All public start nodes must be converted together — you cannot migrate part of a pipeline. The deck's example: migrating Default-Start but not Default-Offline leaves the platform unable to find Default-Offline even though it still exists.
  • Replace pipelets with equivalent script methods where they exist; call the pipelet directly where they do not.
  • Jobs: check whether a system job step does the work; if not, write a custom step as a script module.
  • LINK cartridges: migrate pipeline-based jobs to system or script-module steps. Standalone public pipelines need not be migrated, though doing so reduces technical debt. Any pipeline that calls or is called by storefront functionality must be migrated — and remember a controller cannot call a pipeline start node ending in an interaction-continue node, so those must be converted.

4-2 · Code compatibility modes

A compatibility mode exists for the specific API versions where a change broke backward compatibility — not every version has one. Versioning lets you choose a mode knowingly, accepting the incompatible changes. Salesforce aims for at most two compatibility modes per year.

  • Exactly one mode is active. The platform also keeps a reference to the previously active mode so you can revert. Your available list is: current, previous, and any new mode you may activate.

4-2 · Quotas in depth

The three states are in the quick-glance quota card. Additional mechanics:

  • Quotas monitor resource usage in custom code — memory, app server threads, database table sizes. Exceeding one usually means an inefficient use of a supported capability, and a better solution exists.

4-3 · Monitoring new code, jobs and support cases

After deploying code or receiving a GA platform release, watch for performance change with the Pipeline Profiler (and historically the Object Churn Trends report, which the notes flag as being deprecated). The grid-wide medians to compare against are in the numbers card. Also monitor job performance and search indexing.

Job runtime discipline
  • Anything over an hour gets analysed for optimisation.
  • Job load factor = total job execution seconds on an instance in a day ÷ 86,400. 0.02 is the baseline for an individual job.
  • Keep a master record of median job runtimes so you can see drift.
  • Do not include static resources in daily backups; run impex jobs sparingly; always favour standard imports over custom code for modifying objects.
  • Design impex jobs to recover on their own by recognising which files have not been imported yet.
Network triage

Check for a browser proxy, run a traceroute to find the bottleneck, and read the request waterfall: high waiting time points at the server and needs a code investigation; high receiving time suggests a local network or browser issue; high connecting time also points at the network. If slowness is only from one location, or the whole internet is slow for that user, it is very likely local.

4-4 · Optimisation checklists

Front end

Less JavaScript, simpler CSS and markup; do not inject JavaScript before HTML parsing finishes; compress stylesheets and scripts; move from sprite images to vector graphics and icon fonts (the exception being multiple Google Maps location pins, where Google recommends raster); use current CSS (flexbox, grid); serve images matched to the user's resolution.

Server side

Optimise render time, use a caching strategy that avoids duplicate rendering, and use the platform's own tools to find hot spots: pipeline/controller profiler, technical dashboard, service status, job status, and log analysis across WebDAV and Log Center.

Integration

Ask vendors for SLAs and check them against our best practices. Set timeouts on backend calls and use HTTP caching for non-personalised content. Use the circuit breaker. Define offline behaviour and fallbacks — out-of-the-box tax tables when the tax service is down. Watch front-end integration count, since each one costs client-side performance; a tracking pixel is cheaper than an AJAX call.

Web service troubleshooting sequence

In Business Manager: is the cartridge containing the script on the cartridge path, is the service enabled, and is it set to Live rather than Mocked? In the IDE: does package.json point at the initialisation script, does that script define the service, does the definition include callbacks handling the response, does a script actually call it — and is the service itself reachable?

Performance problems that only appear in production

Frequent database access from inefficient queries or poor cache utilisation; excessive memory from collection mishandling (pulling all orders into a temporary collection, 50,000 promotions on one site); high CPU from calculated attributes across hundreds of object attributes. 5-2 · Keys, certificates and the instance keystore

The keystore holds PrivateKeyEntry and TrustedCertificateEntry items and is encrypted with an internal platform password. Managed at Administration > Operations > Private Keys.

  • Used for web service communication, file transfer over the WebDAV client, dw.net.HTTPClient, and any dw.crypto class taking a KeyRef.
  • Each PrivateKeyEntry holds the private key and its public key.
  • Certificate authorities: the platform trusts only the root CAs shipping with Oracle's Java platform by default. You can add CA certificates to the customer keystore, and they are checked on outbound SSL/TLS connections.
  • Hostnames: for transport-layer use, enter the DNS name the client reaches. The platform selects the certificate by hostname. Comma-separate multiple hostnames. Keys used through a KeyRef need no hostname.
  • The eCDN certificate is separate and goes into the eCDN keystore, not the instance keystore.

5-2 · eCDN and DNS configuration

The embedded CDN accelerates delivery through geographically distributed proxies. It is active only for Development and Production instance types, and custom hostnames need configuring before traffic can be routed.

  1. Aliases: update them on Development and Production. Assign at least one hostname alias matching the instance's current hostname. Without an alias, enabling search-friendly URLs makes every URL except the welcome page return 404.
  2. Zone: configuration is organised by zone, where a zone is a root domain (shop.com) and a hostname is a subdomain (www.shop.com). The platform reads the hostname alias files across all Development and Production instances in all your realms and derives zone names from them. Register the domain with your DNS provider before creating the zone. A zone cannot be deleted through the UI — that needs Support.
  3. DNS: add the cloudflare-verify TXT record and the CNAMEs. The verification value enables communication with the provider after a forced verification and lets you replace a deleted record.
  4. Certificate: upload for the zone. Use a wildcard certificate if you want aliases for development, pre-production and multiple subdomains. Do not update the CNAME until the certificate is installed.
  5. Optional: proxy zones if the merchant has their own Cloudflare account — Support enables this, then you create proxy zones in the B2C Commerce Cloudflare account, add certificates and map origin endpoints. Optional WAF settings and IP allow-listing.
  • Subdomains of one zone can point at different instances and even different realms — www.shop.com on Production, test.shop.com on Development, eu.shop.com on the EU realm's Production.
  • DNS RFC does not allow pointing a root domain directly at the platform; redirect root to subdomain through an external service, and set the redirect up for both HTTP and HTTPS.
  • A merchant should only point their own DNS at the eCDN when they are ready to go live.
  • The eCDN also supports Web Application Firewall and HTTP Strict Transport Security. Enable Enforce HTTPS for all storefronts.

5-2 · Site preferences and disaster recovery

SCAPI — the B2C Commerce API

Introduced July 2020 as a new API infrastructure for headless commerce, and now the only API receiving investment. Architecturally it is stateless and gateway-fronted, in contrast to OCAPI's session-based state and heavier server-side processing.

What it adds over OCAPI
  • An API gateway with multi-tenant support, and an eCDN layer in front of the APIs
  • Rate limiting for reliability; built-in monitoring, metering and logging
  • A more API-driven architectural approach overall
  • New services surfaced only here (discovery, inventory, and everything since)
Shapes to know
  • API families: Shopper APIs (shopper-facing, SLAS-authenticated) and Admin APIs (server-to-server, Account Manager OAuth). Base URL pattern includes a short code and organization id: https://{shortCode}.api.commercecloud.salesforce.com/…/organizations/{organizationId}/…
  • Client id separation: a client id is declared for OCAPI or for SCAPI and cannot serve both, for security reasons.
  • Recent additions (2026): Inventory Lists API, Experiences API for creating and updating Page Designer pages, Shopper Availability API letting clients tune product-information cache TTL, plus verbose SCAPI logging in Log Center with request latency for custom APIs and service runtimes.
  • Deployment note: SCAPI deployments are scheduled per region and outside business hours, so multi-region customers see several trust notifications.

The authentication service for Shopper APIs. It replaces the OCAPI JWT model and is the piece the courseware has no equivalent for at all.

Session bridging — the hybrid-architecture problem

Controllers and APIs use different authentication models, so a hybrid SFRA + headless implementation must keep a SLAS JWT and a dwsid session cookie in sync across login, logout and other shopper events. The documented approach: use the SLAS refresh token to get a new access token, then call the Shop /sessions resource to obtain fresh platform cookies, then reload the page so it renders against the new session. The plugin_slas cartridge implements this for SFRA — keep it current.

Operating it under load

Do not wait for a 401 before refreshing — use the token's full lifetime. Keep to the expected call count for your client type or you will meet 429s. Fix your own 400s, since each one is a failed login. SCAPI supports an external correlation id header (correlation-id with a UUIDv4) that Support can trace.

The AI and agent layer

Agentforce for B2C Commerce agents GA June 2026

Three agent roles: Shopper, Buyer and Merchant agents. For B2C storefronts the relevant one is the Shopper Agent, also called Guided Shopping.

How it is assembled
  1. Enable: in Setup, Commerce Agentforce Settings → toggle on, then enable Agentforce agents. Data 360 is optional but improves personalisation.
  2. Connect: named credentials and external credentials for the commerce API and authentication, remote site settings for the storefront endpoints. Salesforce provides a Concierge cartridge to embed the agent in the storefront and connect it to the Agentforce runtime.
  3. Build: create an agent from the Guided Shopping for B2C Storefronts template in Agentforce Builder. It ships topics and supporting actions — cart management (including resolving a master product to a variant), order assistant, product and cart links, order search, FAQs — and you adjust the topic set by storefront type. PWA Kit storefronts, for instance, drop the Product And Cart Link topic. Global instructions get updated after initial setup.
  4. Deploy: through Messaging for In-App and Web, with an Omni-Channel queue and routing flow targeting the agent, embedded as a web chat channel. Test first in Conversation Preview.
What has landed since GA
  • Gross tax configuration honoured natively in agent cart and checkout flows on both SFRA and PWA storefronts, so agent-quoted prices match storefront gross totals with no mapping work.
  • Attribution reporting: orders and revenue attributed to the Shopping Agent appear in Reports and Dashboards across the Home, Sales, Products and Promotions tabs — the ROI answer for a sceptical stakeholder.
  • Guided questions: rather than filters, the agent asks follow-ups ("what surface are you running on?") and refines results.
  • Launch points: multiple entry points on both SFRA and PWA Kit storefronts; a new React interface that embeds anywhere, matches brand styling, and is aware of the current page and applied filters.
  • Shopper Profile Sync embeds the CRM Contact id in the storefront authentication token, so the agent can act with full customer context — process a return, read real order data.

Agentic Commerce Search 2026

From the Cimulate acquisition announced February 2026, now integrated into B2C Commerce. It replaces keyword matching with an intent model trained on your catalog, real shopper behaviour and simulated queries, and covers four surfaces:

  • Search — natural phrasing, long-tail queries and typos without hand-maintained synonym lists
  • Browse — category pages ranked dynamically from real-time behaviour and stated business targets
  • Recommendations — intent-matched items on PDP and cart
  • Merchandising rules — real-time controls to curate, boost strategic inventory, or bury out-of-stock items

It is natively integrated for B2C Commerce customers (toggle it on, feed it catalog and shopper data) and available headlessly to other platforms. It also feeds the Shopper Agent, so the agent understands the same phrasing. Salesforce cites 13% conversion and 17% add-to-cart improvements from real and simulated shopper data. The related Contextual Search capability adds shopper context — location, season — on top of semantic understanding.

Where this leaves Einstein. Commerce Einstein — product recommendations, predictive sort, search recommendations, Commerce Insights — is still documented and still part of the platform at no extra contract, with the Trailhead content now branded "Agentforce Commerce Einstein". Two years of data is ideal but it becomes useful soon after launch, and it runs on clickstream plus catalog and order feeds, with privacy defaults set in Merchant Tools > Site Preferences > Privacy Settings and Do Not Track handling configurable. Treat Einstein as the incumbent personalisation layer and Agentic Commerce Search as the strategic direction.

Selling through AI channels

  • Native OpenAI integration: map B2C Commerce fields to OpenAI's catalog standards, filter eligible products, and run automated daily syncs so titles, pricing, images and inventory stay accurate inside ChatGPT — without custom code. Shoppers asking ChatGPT for recommendations and gift guides is the use case.
  • Agentic Commerce Protocol with Stripe, plus native ChatGPT and Google integrations, are part of the agentic commerce story Salesforce is building around the platform.
  • Architectural consequence: product data quality stops being only a merchandising concern and becomes machine-readability. Structured, complete, consistent attributes are what gets a product surfaced by an external agent.

Shopper Profile Sync and Data 360

Shopper Profile Sync June 2026

A native, clicks-configured pipeline between B2C Commerce and the core Salesforce org that turns registered digital accounts into unified Person Accounts. It replaces the custom integration plumbing that Lesson 3's Service Cloud module describes building by hand — cartridge, REST service, OCAPI provisioning, hooks, custom objects and a fallback job. Business admins map attributes and manage the sync in Business Manager. It also embeds the CRM Contact id in the storefront authentication token, which is what lets Shopper Agents act on customer context, and it underpins consent capture and post-purchase or abandoned-cart journeys across email, SMS and WhatsApp.

Data 360 connector

B2C Commerce has a native Data 360 connector ingesting commerce data — profile, behavioural and transactional — which is then harmonised into the Data 360 model, where identity resolution links profiles, behaviours and product interactions. Segments built on that dataset can be queried by the storefront in near real time, so promotions, content and offers can react to in-session behaviour instead of waiting for a batch. Ingestion patterns are the usual Data 360 set: bulk from cloud storage or Salesforce clouds, streaming through the Ingestion API, and web/mobile clickstream capture.

Salesforce Payments

  • A native payment solution rather than a per-PSP cartridge integration. Supports Stripe, PayPal and Apple Pay, with Adyen added as an option in release 26.1 so existing Adyen merchant accounts are managed natively alongside other methods.
  • SFRA: delivered as the plugin_commercepayments plug-in; Support must enable the feature switch for the site first; storefront experience configured through the Business Manager Payments module, choosing express and multi-step methods and the service behind each.   • Composable Storefront: requires PWA Kit 3.17 or later. Salesforce Order Management

The courseware's OMS discussion is mostly about third-party systems, with a note that the legacy Gillian cartridge and the old Commerce Cloud OMS are closed to new customers. The current answer is Salesforce Order Management on core, separately licensed, with a productised B2C Commerce connection.

Security, operations and tooling

eCDN: WAFv2, custom rules and Logpush

The deck's eCDN section stops at "optional — update WAF settings, allow-list IPs". That is now a substantial configuration surface with two mandatory migrations behind it.

ChangeWhat happened
Firewall rules → custom rulesFirewall rules were deprecated on 6 February 2024; existing rules were migrated to eCDN custom rules and are managed through the custom rule endpoints. Custom rules give full control of the rule expression, more request field types and more actions.
WAFv1 → WAFv2Introduced in release 24.7 as self-service migration from the Business Manager WAF tab; all zones had to be migrated by 1 February 2025.
  • WAFv2 rulesets: a Salesforce eCDN managed ruleset, the Salesforce eCDN OWASP Core Ruleset (tracking the OWASP ModSecurity CRS), and an exposed-credentials check against a public breach database. Some rules ship disabled or log-only to limit false positives — enabling a ruleset keeps each rule's default status, so use individual rule overrides to change one.
  • Tuning false positives: turn on Logpush with firewall_events, find the offending rule, then override its action or disable it. For OWASP noise, adjust paranoia level and score threshold. A custom rule with the skip_wafv2 action lets specific requests bypass WAFv2 entirely; other skip actions cover custom rules and rate limiting.
  • Rule evaluation: custom rules run in listed order; managed_challenge, js_challenge, legacy_captcha, block and skip_custom_rules stop further evaluation.
  • Per-instance: WAFv2 settings are configured separately for Development, Staging and Production and are not replicated — which is deliberate, so you can promote security settings through environments.
  • 2026 additions: legacy access rules migrated to Business Manager WAF custom rules and Managed IP Lists, so trusted traffic is controlled realm-wide instead of zone by zone. On-demand sandboxes can now be provisioned with eCDN features, so caching logic, WAF rules and security configuration are testable in an environment that matches production. V1 zones are being migrated to V2 zone configurations.

Observability: from log-reading to alerting

  • Anomaly Detection: production-ready, AI-driven monitoring of system logs that surfaces unusual patterns in real time — order or payment failures, error spikes, failed logins, bad login patterns, security threats — with custom filtering and root-cause context. This is the answer to Lesson 4's manual log-scrubbing workflow.
  • Unified alert management: one page across all Log Center data sources, with alerts for events, log streaming and anomaly detection, notification channels extended to Slack and PagerDuty, and state-aware alerts that fire on new, ongoing and resolved rather than repeating.
  • Granular replication events (pilot): notifications when specific objects finish replicating — product ids, price tables, content assets, promotions, catalogs — enabling precise cache invalidation without waiting for a full replication cycle. Directly relevant to the "avoid full cache clears" problem in Lesson 4. Shopper registration events fire on account creation for real-time onboarding journeys.
  • Asynchronous Eventing Framework (pilot): event-driven architecture support, launching with real-time asynchronous notifications during replications.
  • Granular replication targeting specific content assets, and browser-console debugging for Page Designer page caching, also appear in 2026 releases.
Breaking change to watchThird-party libraries have been upgraded to enforce strict RFC 6265 cookie rules. Custom code emitting non-compliant cookies needs cleaning up on an on-demand sandbox before the change lands.
